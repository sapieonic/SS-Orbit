Shanmukha Agritec · Orbit Shifting · implementation proposal

Orbit Shifting Build Plan ఆర్బిట్ షిఫ్టింగ్

How to build the Farmer app, Field Assistant app and Head Office dashboard on one backend. It covers the architecture, the hard parts, and the order to build in so that something useful reaches the field in about 12 weeks.

Inputs: Requirements v1.0 (58 IDs), 53 wireframe screens, MoM 17-10-26 Stack: Go · Flutter · React · PostgreSQL Reviewed by: an independent architecture review (Fable model), changes folded in Date: 30 Oct 2026

The recommendation in one screen

Build one modular Go backend on PostgreSQL, two Flutter apps that share a set of packages, and one React admin portal. Ship the FA side first, because farmers only see value once FAs are logging visits.

Backend

One modular monolith, not microservices

One Go codebase whose internal packages match the Orbit Core modules in the doc (8 built: identity, geo, farmers, masters, visits, messaging, sync, audit; calendar, adapters and money come with their phases). It builds into two small binaries, an API and a worker. This is the right size for about 5,000 farmers and 25 FAs, and modules can be split out later if needed.

Database

PostgreSQL holds the data, Redis keeps it fast

One farmer database (SYS-01). PostGIS handles plot boundaries, acreage and nearest-first lists. Background jobs stay in Postgres (River), so a job is saved in the same transaction as its data. Redis caches weather, masters and FA territories and rate-limits OTPs. It is never the source of truth.

Mobile

Two Flutter apps, shared packages

The farmer app stays small, online-first and Telugu-first with voice. The FA app is offline-first and keeps its whole territory on the phone. Both use one design system, one API client and one Telugu/English string set.

Offline sync

Commands up, territory snapshot down

Every FA action is queued on the phone as a command with its own ID. The server applies it once, even if it is sent twice. The phone then re-downloads its whole territory (well under 1 MB). This is simple and safe, and it can't silently lose a visit.

Money

Ledger, maker-checker, webhooks as truth

Cashback lives in an append-only double-entry ledger. Razorpay and payout webhooks decide what is paid. Above ₹5,000 a second person must approve, and the person who approved a bill can't release its payout.

Sequence

FA pilot at week 12, money live for Kharif 2027

Phase 0 closes the business decisions. Phase 1a pilots the FA app with 5 FAs in one mandal during Rabi. The farmer app launches by end of March. Premium and cashback go live in early June, before Kharif sowing.

Architecture

Each module is a Go package under internal/ with a small service interface. A module talks to another only through that interface or a domain event, never by reading the other module's tables. golangci-lint (depguard) blocks imports of another module's internals. This keeps the option of splitting a module out later (payouts is the likely first one) without a rewrite.

Caching with Redis

Redis sits beside Postgres (dashed in the diagram above) to make common reads fast and to rate-limit OTPs. Postgres stays the only source of truth. If every Redis key were lost, the apps would only get slower for a few minutes.

Rules

  • Cache-aside: read Redis, and on a miss read Postgres and fill the key. Writes go to Postgres first, then delete the key rather than update it, which avoids stale-write races.
  • Versioned data (masters, territories) uses the version in the key, so a new version is a new key and the old one simply expires.
  • Every key has a TTL. Keys are namespaced by environment (prod:masters:v42).
  • Money is never cached: cashback balance, ledger, invoice state and payout status are always read from Postgres. The home summary leaves the balance out.

If Redis is down

  • Reads fall back to Postgres. The apps get slower but keep working.
  • OTP rate limits fall back to a Postgres counter. Login keeps working, but OTP sending is never unlimited. This blocks SMS-pumping fraud, which is billed per Telugu SMS.
  • Production uses ElastiCache with a replica across availability zones, with an alert on health.
  • Jobs are not affected, because River runs on Postgres.

Data model

Everything hangs off farmer → plot → season, as the doc's SYS-03 rule says. The model enforces that rule with non-null foreign keys, so nobody has to remember it.

  • IDs are UUIDv7, minted on the phone, so records created offline already have their final ID.
  • No competitor brands are stored (FA-09). Advice can point only to a Shanmukha SKU or to "salt only". There is no free-text product field to leak into.
  • Audit and ledger tables are written by a database role that has no UPDATE or DELETE rights, and they are exported nightly to S3 with Object Lock. That gives tamper evidence without hash-chaining rows.
  • Season rollover is explicit: at season end, the FA or farmer confirms the next crop on each plot. Premium validity is tied to the season (e.g. "valid till 31 Mar 2027").

Mobile apps

Two apps rather than one app with a role switch. They differ in users, login, offline depth and how they are distributed, and the farmer app has to stay small and light on data.

Farmer app

  • Online-first, with a Drift cache of Home, visits, advisories and last-saved weather. Bills and service requests go into an outbox and are sent when the phone is back online (matches the "no internet" states in the wireframes).
  • Telugu by default, a Listen button on every screen, icon-first tiles, one task per screen.
  • OTP autofill uses the SMS Retriever API, with a "call me with the OTP" fallback. It never asks for the READ_SMS permission (Play Store policy).
  • Razorpay Checkout opens the farmer's UPI app, and the farmer always types their own UPI PIN. When the app is reopened it asks the server for the order status as well as waiting for the webhook.
  • Sign-up flow: phone → OTP → consent → pick your village (voice-assisted list). The village step was missing from the wireframes, and the new-farmer alert can't reach the right FA without it.
  • Target: Android 8+, under 20 MB download, tested on ₹7–10k phones.

FA app

  • Offline-first. The whole territory (farmers, plots, open visits, recent history, masters) lives in Drift on the phone.
  • Login once with the HO-issued ID and password, then a 4-digit PIN unlocks the app offline for up to 7 days. The refresh token is encrypted with a key derived from the PIN and the Android Keystore. Too many wrong attempts wipe local data.
  • GPS boundary walk with an accuracy gate (for example "±28 m is too rough"), with a fallback to typed area plus a pin. Area is recomputed on the server in PostGIS.
  • Offline map tiles for the territory. The tile provider's licence must allow offline caching (a Phase 0 check).
  • Photos are compressed on the phone (~200 KB) and uploaded after their visit has synced, with an optional Wi-Fi-only setting.
  • Distributed through a Play closed testing track or a login-gated listing. Managed Google Play would need Android Enterprise enrolment on FAs' personal phones.

Shared Flutter packages

orbit_ui (large, high-contrast components that read well in sunlight, Telugu type), orbit_l10n (ARB string files, Telugu + English, with the audio file key for each prompt), orbit_api (generated client), orbit_core (auth, HTTP, storage, logging, feature flags, forced update), orbit_media (camera, compression, upload queue) and orbit_voice (playback of recorded and TTS audio). Golden tests render each screen in Telugu, so clipped text is caught early.

FA offline sync

This is the part most likely to go wrong, so it is kept deliberately simple. An FA's territory is a few hundred farmers, which compresses to well under 1 MB. At that size, re-downloading the whole territory is cheaper and safer than tracking changes row by row.

Why there are few conflicts

  • Most FA data is append-only (visits, photos, invoice decisions). New records never clash.
  • Enrolment of a phone number that already exists is merged on the server, which returns "merged into Raju P". This matches the "Already registered" wireframe.
  • Commands carry the record ID, so a retry after a timeout is applied once, not twice.

When there is a real conflict

  • Editable records (plot area, farmer profile) carry an expected_version.
  • If HO changed the record while the FA was offline, the server rejects that one command and returns both values.
  • The app shows the wireframe's choice: Yours 1 ac 30 gunta · HO's 2 ac 0 gunta → Keep mine / Keep HO's. The choice is logged.

If territories ever grow past a few thousand farmers, the snapshot can switch to a per-row change feed. The command side stays the same either way. PowerSync was considered and dropped: writes would still need our own API, and it adds a hosted dependency without native PostGIS support.

Web apps

There is one full web app, the HO admin portal, and a small set of farmer web pages. Full web copies of the farmer and FA apps are not recommended for launch. Farmers are on Android, and the FA app's value is that it works offline.

Admin portal (React)

  • Screens from the wireframes: Overview, Farmers, Farmer detail, FAs & logins, Villages & allocation, HO users & roles, Send advisory, Cashback & services (Services, Invoices, KYC, Payouts), Masters, Analytics, Messages, Audit log.
  • The same app has a responsive phone view for the "Today" queue and bill approvals (H10). It can be installed as a PWA.

Money flow

This is where fraud and reconciliation problems would cost real money, so it gets the most controls. A bill moves through fixed states. Every state change is a ledger entry or an audit entry.

Fraud controls

  • Duplicate detection: bill number + dealer, plus a perceptual hash of the photo, so the same photo re-shot is caught.
  • Cashback is capped at 5% of MRP × quantity from the SKU master, so an inflated bill doesn't pay more.
  • Per-farmer cap per season. Bills from dealers not yet verified wait.
  • The FA who advised a product is also its first checker, so HO re-checks a random sample. Anomaly views flag unusual dealer and FA patterns.

Identity check, without Aadhaar

  • The check exists to stop payout fraud. Shanmukha is not a regulated entity, so it doesn't need full KYC.
  • The farmer's UPI ID is validated with the payout partner, which returns the bank account name to match against the profile. Add a selfie and a Finance review, as in the H4 KYC wireframe.
  • No Aadhaar photo or number is collected. If Finance wants a document, use Voter ID or PAN and store the last 4 digits only.
  • Files go in a separate KMS-encrypted bucket. Every view is logged.
For Finance to decide before Phase 2: whether cashback paid to farmers attracts TDS under section 194R once a farmer crosses ₹20,000 in a year, which would need PAN and a TDS ledger account. Also the GST treatment of a post-sale discount. In legal and vendor copy, call it a "cashback balance", not a "wallet", so it isn't read as a prepaid instrument under RBI rules. The Telugu UI label వాలెట్ can stay.

Messaging and compliance

Getting messages delivered in India has rules that take weeks of approvals. These have to start in Phase 0, or they will hold up the launch even if the code is ready.

How an advisory goes out

  • Compose (HO or CIV) → target by crop, area, stage and plan → save a recipient list per farmer (FAR-13) → fan out per channel in batches → provider callbacks update the status for each farmer.
  • Quiet hours 9 pm to 7 am for advisories. OTP and payment messages go out at any time.
  • An advisory that names a product needs Agronomy approval, and it is promotional for SMS and marketing-class for WhatsApp. Plain crop advice is a service message. The composer classifies each message and picks the right template.
  • "Listened" is counted from plays on the in-app or web audio page. Failed deliveries can be retried, or sent to FAs as a call list.

Compliance checklist

  • TRAI DLT: entity, sender header and every SMS template registered. URLs inside SMS must be whitelisted. Telugu is sent as Unicode SMS (shorter segments, higher cost).
  • WhatsApp Business: business verification and template approvals. No audio in templates.
  • DPDP Act 2023: consent per purpose and per partner (already in the wireframes), notice in Telugu, a named grievance officer, retention and erasure rules, a 72-hour breach process.
  • Play Store: no READ_SMS, Financial Features declaration, foreground-only location for FAs, data safety form.
  • Data residency: all storage in an India AWS region.

Repositories and shared code

Create one repository for everything: backend, both Flutter apps, both React apps and infrastructure, each in its own top-level folder. Go, Dart and TypeScript can't share code directly, so sharing is built around three single sources (the API spec, design tokens and farmer-facing strings) that are generated into each toolchain.

When to split further: if an outside agency builds one of the apps, or the team grows past about 25 engineers, move that app into its own repo. It would then consume the generated client as a published package from a private pub or npm registry. Nothing in the layout below blocks that.

Rules that keep shared code healthy

  • Generated code is committed. CI runs task gen and fails if anything changed, so reviewers see every API change in the pull request.
  • No breaking changes to the mobile APIs. Old app versions stay on farmers' phones for months. oasdiff fails any pull request that breaks /v1/farmer or /v1/fa. Changes are additive, or go to /v2. A forced update is the last resort.
  • Rule of two. Code moves into a shared package only when a second app needs it. Feature screens stay inside their app.
  • One-way dependencies. Packages never import apps. Go modules call each other only through their service interface, and internal/platform holds no business logic.
  • CODEOWNERS. contracts/ needs a backend reviewer plus one client reviewer. invoices/, payouts/, identity/ and infra/ need the tech lead.
  • Release by tag per deployable: backend/v1.4.0, admin/v1.2.0, farmer-app/1.3.0+45, fa-app/1.0.3+12. Development is trunk-based with short-lived branches, and feature flags cover the TBC items.
  • One command for local dev: task dev starts Postgres, Redis, MinIO and fake partner servers. Nobody needs Razorpay or SMS credentials to work on a feature.

Guarding production with infra in the same repo

  • Plan on every pull request that touches infra/, with the Terraform plan posted as a comment for review.
  • Apply only from main, through a GitHub production environment with two required reviewers. Dev and staging apply automatically.
  • No AWS keys anywhere. The workflow gets short-lived credentials through GitHub OIDC, and only the production-environment job can assume the prod role.
  • Secrets stay out of the repo. Razorpay, payout, SMS and WhatsApp keys live in AWS Secrets Manager and are referenced by name only.
  • A deploy is a one-line pull request in infra/envs/prod that changes the image tag, which also leaves a clean record of what ran when.

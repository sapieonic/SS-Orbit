# Web apps: implementation plan

## Purpose

How to build the two React apps in `web/` against the backend as it is today: the HO admin portal
(`apps/ho-portal`, desktop + phone view) and the small farmer web pages opened from SMS links (`apps/farmer-web`).
A new developer should be able to start from this file alone. Where the build plan names a tool, it is used here;
where the plan is silent, the choice is marked **(recommendation)**.

  (also https://claude.ai/artifact/M85KFgHynuZ4gWBqz87pSa): sections "Web apps", "Logins and roles", "Inside the repo", roadmap.
- `backend/docs/CONVENTIONS.md` section 4 (surfaces, guard, error shape, pagination). The rest is backend-internal.
- `contracts/ENDPOINTS.md`: every operation by surface. `contracts/openapi/*.yaml`: one spec per module

## Decisions (fixed)

- One pnpm workspace in `web/` with Turborepo (plan). Apps: `ho-portal`, `farmer-web` (the plan calls the first one
  `apps/admin`; this repo uses `ho-portal`).
- React 19, Vite, TypeScript (strict), TanStack Router / Query / Table, shadcn/ui + Tailwind, react-hook-form + zod
  (plan). Maps on web use MapLibre (plan).
- TypeScript client generated by **orval** with TanStack Query hooks from `contracts/openapi` (plan). Generated code is
  committed; CI fails if it is stale.
- Look and feel from `design/tokens/` (CSS variables + Tailwind theme in `packages/ui`); farmer-facing words from
  `i18n/te.json` and `i18n/en.json`. The admin UI is English, with Telugu previews of farmer-facing text (plan).
- HO auth: email + password + TOTP for every HO user, 8 h absolute session, roles admin/agronomy/finance/ops plus
  optional district scope. The UI hides what a role can't do; the server enforces it anyway.
- Static hosting: S3 + CloudFront from `infra/` (plan). No server-side rendering.
- No full web copies of the farmer or FA apps.

Package rules: packages never import apps; `api-client` knows nothing about the session (it takes `getAccessToken`

### Generated API client (`packages/api-client`)

Generate from the one web bundle, `contracts/build/web.yaml` (committed; `make specs` in `backend/` rewrites it
with `tools/bundle-specs.py`). The bundler has already merged the shared components and fails on any schema-name
clash across specs, so one output folder is enough.

```ts
// web/packages/api-client/orval.config.ts
import { defineConfig } from 'orval';
export default defineConfig({
  orbit: {
    input: { target: '../../../contracts/build/web.yaml' },
    output: {
      mode: 'tags-split',
      target: 'src/gen/orbit.ts',
      schemas: 'src/gen/model',
      client: 'react-query',
      httpClient: 'fetch',
      clean: true,
      override: {
        mutator: { path: 'src/http.ts', name: 'orbitFetch' },
        query: { useQuery: true, useInfinite: true, useInfiniteQueryParam: 'cursor', signal: true },
      },
    },
  },
});
```

Commands (run in `web/`):

```
pnpm install
pnpm --filter @orbit/api-client gen        # script: "orval --config orval.config.ts && prettier -w src/gen"
pnpm gen:check                             # root script: pnpm -r gen && git diff --exit-code -- packages/api-client/src/gen
```

After a spec change: edit `contracts/openapi/<module>.yaml`, run `make backend-gen` (Go side) and
`make backend-specs` (`ENDPOINTS.md` + bundles) from the repo root, then `pnpm gen` here, all in the same PR. Check the generated mutator
call signature after the first run and match `orbitFetch` to it (orval's fetch-client signature has changed between
minor versions; pin orval exactly in `package.json`).

Hand-written files next to `src/gen/`:
- `http.ts`: `orbitFetch<T>(url, init)`. Prefixes the base URL from runtime config, sets `Authorization: Bearer`,
  `Content-Type: application/json` (or `text/csv` for the village import), parses JSON, returns `undefined` on 204,
  throws `ApiError` on non-2xx. On 401 with an expired access token it asks `auth` to refresh once and retries.
- `errors.ts`: `class ApiError { status; code; message; details; requestId; retryAfter }` built from
  `{ "error": { code, message, details } }`, `X-Request-ID` and `Retry-After` (both exposed by the CORS middleware).
- `paging.ts`: `getNextPageParam = (p) => p.next_cursor ?? undefined` and a cursor-stack helper for Previous/Next.

### Auth and session (`packages/auth`)

Exactly as the API works (identity spec, `hoLogin` and friends):

1. **Login form**: email, password, 6-digit code (code optional in the UI, hint "leave empty on your first sign-in").
   `POST /v1/auth/ho/login` with `totp_code` only when typed.
   - 200 `HOSession { tokens, user, must_change_password }` -> store tokens, go to step 4 if `must_change_password`.
   - 401 `totp_enrolment_required` (only after a correct password) -> step 2.
   - 401 `unauthorized` -> one generic message ("email, password or code is wrong"). A blank code for a user who has
     TOTP is also this, and counts as a failed attempt, so say "enter the code from your authenticator app".
   - 401 `temp_password_expired` -> "Your temporary password is older than 72 hours. Ask an admin to reset it."
   - 429 `rate_limited` -> disable the button for `Retry-After` seconds.
2. **TOTP start**: `POST /v1/auth/ho/totp/start {email, password}` -> `{ otpauth_url, secret }`. Render
   `otpauth_url` as a QR code client-side (`qrcode` npm package, recommendation; never send it to a third-party QR
   service) and show `secret` in groups of 4 for manual entry. Keep email/password in component state only.
   409 `totp_already_enabled` -> back to login with the code field focused.
3. **TOTP confirm**: `POST /v1/auth/ho/totp/confirm {email, password, totp_code}` -> `HOSession` (signs in).
   400 `totp_invalid` / `totp_not_started` -> inline error on the code field. Then clear the secret from memory.
4. **Temporary password**: while the token has the must-change flag, every route except `/v1/admin/me`,
   `/v1/admin/me/password` and `/v1/auth/*` answers 403 `password_change_required`. The router guard sends the user to
   Change password; `POST /v1/admin/me/password {current_password, new_password}` (8+ chars, a letter and a digit)
   -> 204 -> **immediately `POST /v1/auth/refresh`** to get a token without the flag (the current access token keeps
   it). The change signs out the user's other sessions. Any 403 `password_change_required` seen anywhere also
   routes here.
5. **Who am I**: `GET /v1/admin/me` -> `HOUser { id, email, name, role, district_ids, status, totp_enabled, ... }`.
   Load it after login and after every refresh (role and districts can change; they take effect at the next refresh).
   `district_ids` empty = all districts.
6. **Refresh**: access tokens live 15 min (`ACCESS_TOKEN_TTL`); HO refresh tokens rotate on every use and the HO
   session has an **absolute 8 h end** (`REFRESH_TTL_HO=8h`; rotation keeps the family's original `refresh_expires_at`).
   - Refresh proactively ~60 s before `access_expires_at`, and reactively on a 401 whose `details.reason` is `expired`.
   - **Single-flight**: one refresh at a time per browser, not just per tab. Use the Web Locks API
     (`navigator.locks.request('orbit-ho-refresh', ...)`); inside the lock re-read storage and skip the call if another
     tab already refreshed. Queue other requests behind the in-flight promise.
   - **60 s retry grace**: if the refresh request fails on the network, retry with the same refresh token within 60 s;
     the server returns the same successor. Never retry an old token after storing a new one: reuse outside the grace
     is 401 `refresh_reused` and revokes the whole session.
   - Show "Your session ends in 5 minutes, save your work" before `refresh_expires_at`; after it, back to login.
7. **Signed out by the server**: 401 `session_revoked` (admin disabled the user or signed them out), `refresh_reused`,
   `unauthorized` after a refresh, or a refresh 401 -> clear storage, broadcast to other tabs, go to login with a reason.
8. **Logout**: `POST /v1/auth/logout {refresh_token}` (always 204), clear storage, broadcast.

**Token storage (decision for the browser, recommendation)**: the API is bearer-only; there are no auth cookies
(the CORS middleware sends `Allow-Credentials` but nothing uses it). Keep the access token in memory and the token
pair in `localStorage` under one key, synced across tabs with the `storage` event / `BroadcastChannel`. Why: HO
staff work in several tabs (open a farmer in a new tab), `sessionStorage` would force a TOTP login per tab, and
memory-only would force one per reload. The exposure is bounded by the 8 h absolute session and server-side
revoke. Mitigate XSS with a strict CSP (below), no third-party scripts, no `dangerouslySetInnerHTML`. If security
review rejects this, the alternative is an httpOnly refresh cookie, which needs backend work (a cookie-issuing
refresh endpoint plus CSRF protection). It is on the backend backlog (item 12); don't fake it in the client.

**CORS**: the portal is on its own origin in staging/prod (e.g. `https://ho.<domain>`) calling the API host, so
`CORS_ORIGINS` on the API must list that origin exactly (`*` is refused in prod). In dev, use a Vite proxy
(`/v1` and `/dev` -> `http://localhost:8080`) so CORS doesn't matter; the default `CORS_ORIGINS`
(`http://localhost:5173,http://localhost:3000`) covers direct calls from both dev servers.

Implementation: a `can(action)` function in `@orbit/auth` built from `me.role` and `me.district_ids` using this
table (one place, unit-tested). Hide nav items and buttons the user can't use. Still handle 403 everywhere: the
server messages are human-readable ("only Agronomy can approve or reject dose and product changes"), so show
`error.message` as is. Scoped users get 404 for FAs outside their districts; treat it as "not found", not an error.

**Maker-checker UI**
- Advice rules (`/v1/admin/masters/rules`): a version's `status` is `draft | approved | superseded | rejected`;
  `draft` with `submitted_at` set means "waiting for Agronomy". Author sees Edit (`PUT .../rules/{id}`) and Submit
  only while unsubmitted. Approve/Reject shows only when `me.role == agronomy`, `created_by != me.id` and the draft is
  submitted; for everyone else show the wireframe's note "Only Agronomy can approve dose and product changes".
  Reject needs a note. Approve can return 409 `issue_has_live_rule` ("another rule is already live for this issue and
  salt"): show it and link to the live rule. "Edit, as a new draft" = `POST .../rules` with `rule_key`
  (409 `draft_exists` -> open the existing draft; 409 `rule_exists` on a new rule -> open that rule's history).
- Advisories: `names_product: true` sends the advisory to `pending_approval` on submit. If the text mentions an active
  product or salt name and `names_product` is false, create/submit return 400 `validation_failed` with
  `details.fields.names_product` naming the term. Show the message under the toggle, offer "Mark as naming a product",
  and resubmit. Approve/Reject: agronomy, and neither the author (`created_by`) nor the last editor (`updated_by`);
  hide the buttons for both and still handle the 403.

## Screen-by-screen map

All lists use `?limit=&cursor=` and return `{ items, next_cursor }` (keyset, opaque cursor, default 50, max 200).
Keep filters and the cursor stack in the URL search params (TanStack Router `validateSearch` with zod) so a filtered
view can be shared. `next_cursor: null` = last page. Changing a filter resets the cursor; 400 `invalid_cursor` also
resets it.

### H7 Farmers and Farmer 360

- List: `GET /v1/admin/farmers` with `district_id, mandal_id, village_id, fa_id, unassigned, crop_id, status, plan, q`
  (`q` = name in English/Telugu, or phone when 4+ digits). Phones come masked. Map `active_crop_ids` to names from
  `GET /v1/admin/masters/crops`. Mandal filter from `GET /v1/admin/geo/tree`.
- Bulk reassign: `POST /v1/admin/farmer-reassignments {to_fa_id, farmer_ids[<=1000], from_fa_id?}`; with
  `from_fa_id`, only farmers currently with that FA move. "Move an FA's farmers in a village":
  `{to_fa_id, from_fa_id, village_ids[<=100]}` (`from_fa_id` required here; only that FA's farmers move, unassigned
  farmers don't, so pick those by `farmer_ids`). Exactly one of `farmer_ids` / `village_ids`; `from_fa_id` must
  differ from `to_fa_id`. Result `{moved, farmer_ids}`; inactive farmers and farmers already with that FA are
  skipped; farmers get an SMS. FA picker: `GET /v1/admin/allocations?village_id=` /
  `?mandal_id=` to suggest the FAs who cover the area. Scoped users: 403 if the FA has no allocation in their districts.
- Farmer 360: `GET /v1/admin/farmers/{id}` -> profile (`Farmer` with `version`), `photo_url` (presigned for
  15 min; refetch on image error), village, assigned and enrolling FA, current consents + history, plots with
  GeoJSON and seasons. Draw plots with MapLibre (tile source is an open
  decision). Visits panel: `GET /v1/admin/visits?farmer_id=`. Devices (admin/ops): `GET /v1/admin/devices?subject_kind=farmer&subject_id=`.
  Audit trail link: `GET /v1/admin/audit/chain/farmer/{id}` (unscoped admin/finance/ops only).
- Edit: `PATCH /v1/admin/farmers/{id}` with `expected_version` (required) plus changed fields (`name, name_te,
  language, village_id, phone, plan, reason`). 409 `version_mismatch` (`details.current_version`): reload, show what
  changed, let the user re-apply. 409 `phone_taken`. Plan change: admin only, `reason` required (audited as
  `farmers.plan_changed`). PATCH can't clear optional fields (known gap).
- Deactivate / reactivate: `POST .../deactivate` / `.../reactivate {reason?}`; confirm dialog explaining that the
  farmer leaves FA snapshots and advisory targeting.
- Season rollover (admin/ops): `POST /v1/admin/season-rollovers {season_code, outcome?}`; `season_code` like
  `rabi-2026-27` or `kharif-2027`; `outcome` `harvested` (default) or `abandoned`. Make the user type the season code
  to confirm; show `{closed}`.
- Season codes follow the server calendar (IST): `summer-YYYY` Apr-May, `kharif-YYYY` Jun-Oct, `rabi-YYYY-YY`
  Nov-Mar. Only the farmer and FA surfaces return the open list (`season_codes`), so the rollover form checks the
  pattern and asks the user to confirm.
- Gaps: "Add farmer" (H7), "Export CSV", "Send advisory" to selected farmers (advisory targets have no `farmer_ids`),
  one farmer's notices in the activity feed, Wallet/KYC columns (Phase 2).

### H2 FAs and logins

- List: `GET /v1/admin/field-assistants?q=&status=&not_synced_since=` (`active | leaving | inactive`). "Not synced
  24 h" = `not_synced_since=<now - 24 h>` (also returns FAs who never synced). Area column: load `GET /v1/admin/allocations` (all
  pages; a few hundred rows) and group by `fa_id`. Visits/week: `GET /v1/admin/visits/counts` for this week.
  Farmers per FA: no count endpoint (gap); link to the farmers list filtered by `fa_id`.
- Issue login: `POST /v1/admin/field-assistants {name, phone, level, code | area_code, name_te?, languages?, working_hours?}`.
  Response `{field_assistant, temp_password}`: show the password **once** in a `OneTimeSecret` dialog with copy
  button and "it won't be shown again"; don't keep it in the query cache, logs or analytics. 409 `code_taken`,
  409 `code_space_full` (area code ran out of numbers).
- Detail / edit: `GET` and `PATCH /v1/admin/field-assistants/{id}` (empty string clears `name_te`,
  `working_hours`, `photo_key`; login ID never changes).
- Status: `POST .../status {status}`. Warn that `inactive` signs the FA out and wipes their devices.
- Reset password: `POST .../reset-password` -> `{temp_password}` once; signs the FA out everywhere.
  Sign out all devices: `POST .../sign-out` (204).
- Devices: `GET /v1/admin/devices?subject_kind=fa&subject_id={id}` (revoked included);
  `POST /v1/admin/devices/{device_id}/revoke {reason}` (reason required) -> app wipes itself at next contact.
- Hand over territory: see Allocations below.

### H2 Villages and allocation (ADM-04)

- Tree: `GET /v1/admin/geo/tree` (districts -> mandals with `village_count`). Villages:
  `GET /v1/admin/geo/villages?mandal_id=&district_id=` (paged) or `?q=` (best matches, `next_cursor` null).
- Add/edit: `POST/PATCH /v1/admin/geo/districts|mandals|villages`. 409 `district_exists`, `mandal_exists`,
  `village_exists`, `lgd_code_taken`. Villages can't change mandal; mandals can't change district.
- CSV import: `POST /v1/admin/geo/village-imports?create_missing=true|false`, body is the raw file with
  `Content-Type: text/csv` (not multipart). Columns: `district, mandal, village` required; `name_te, lgd_code, lat, lng`
  optional. All or nothing: 400 `validation_failed` with `details.fields` keyed `"row N"` -> render a row-error
  table. 409 `lgd_code_taken` with `details.row`. Over 5 MiB -> 413. Result `{rows, created, updated, unchanged,
  districts_created, mandals_created}`.
- Allocations: `GET /v1/admin/allocations?fa_id=&district_id=&mandal_id=&village_id=&include_ended=`.
  Create `POST /v1/admin/allocations {fa_id, level, area_id, is_lead?}`. **409 `area_has_lead`** (`details.fa_id`,
  `details.allocation_id`): dialog "X is already the lead here: add as support FA, or end X's allocation and make
  this FA the lead" (the second option = `POST /v1/admin/allocations/{allocation_id}/end` then create again).
  409 `allocation_exists` (same FA, same area). End: 409 `allocation_ended`.
- Hand-over (two calls today; one call is backend backlog item 9):
  1. `POST /v1/admin/allocations/handover {from_fa_id, to_fa_id}` -> `{ended_allocation_ids, allocations,
     affected_village_ids}`. Idempotent: a repeat moves nothing.
  2. Move the farmers: `POST /v1/admin/farmer-reassignments {from_fa_id, to_fa_id, village_ids}` with
     `affected_village_ids` in chunks of 100. Only the old FA's farmers in those villages move; other FAs' farmers
     sharing a village stay. A repeat moves nothing more.
  3. Optional: `POST /v1/admin/field-assistants/{from}/status {status: inactive}` ("deactivate on hand-over").
  Show progress per step and make each step retryable. Open visits and callbacks follow the farmers (server event).

### H5 Masters (ADM-08)

Header shows `GET /v1/admin/masters/version` ("approved changes reach the apps at their next sync").
- Crops & stages: `GET/POST /v1/admin/masters/crops`, `GET/PATCH .../crops/{id}` (code permanent),

### Farmer web: voice-note notice page

Route `/web/notices/:id?t=<token>` in `apps/farmer-web` (Vite `base: '/web/'`). The backend builds the SMS link as
`{FARMER_WEB_BASE_URL}/web/notices/{id}?t={token}` (`WEB_LINK_TTL`, 7 days; `FARMER_WEB_BASE_URL` defaults to
`PUBLIC_BASE_URL`). In prod the farmer-web CloudFront distribution (its own host, or the short-link domain) serves
`/web/*` from the farmer-web bucket and forwards `/v1/web/*` to the API uncached, so the page calls the API on its
own origin (no CORS).

- On load read `t`, keep it in memory and `sessionStorage`, and remove it from the address bar with
  `history.replaceState`. Send it as `Authorization: Bearer` (allowed for `/v1/web/*`) rather than `?t=`, so it
  doesn't land in CloudFront/ALB logs on API calls (the API's own access log records the path only). Set `<meta name="referrer" content="no-referrer">`.
- `GET /v1/web/notices/{id}` -> `Notice` (Telugu title/body first, English if present, `sender` tag HO/CIV,
  `audio_url` presigned and short-lived). One big Listen button (`<audio>` controls hidden behind it); on the first
  `play` event `POST /v1/web/notices/{id}/listened` (204, idempotent; also marks read). If the audio URL has expired
  (error event), refetch the notice and play again.
- Errors in Telugu with an English line: 401 (link expired: "open the Orbit app or call your FA"), 403 (link is for
  another page), 404.
- Budget: initial JS under ~60 KB gzip (recommendation; NFR-05 2G). No router, no TanStack Query, no UI kit beyond
  tokens and fonts: call the generated fetch functions or plain `fetch`. Fonts: Noto Sans Telugu, subset, `font-display: swap`.
- Dev: run farmer-web on `:3000` with a Vite proxy for `/v1` and `/dev` to `:8080`, and set
  `FARMER_WEB_BASE_URL=http://localhost:3000` in `backend/.env` so printed SMS links (log SMS sender) open the dev
  page.
  Mint a test token from `backend/`: `go run ./cmd/devtoken -kind web -id <farmer_id> -purpose notice:<notice_id>`.
- Later pages (product card with dealers, payment receipt) are Phase 2; the product card needs a farmer SKU detail
  endpoint (backlog).

## Error handling

One shape: `{ "error": { "code", "message", "details" } }`. One `ApiError` class, one place that maps it:

| Status / code | UI |
|---|---|
| 400 `validation_failed` | Map `details.fields` (`{name: reason}`) onto react-hook-form with `setError`; dotted names (`target.plan`) map to nested fields; `"row N"` keys go to the CSV error table; unknown keys go to a form-level banner |
| 400 `invalid_request`, `invalid_cursor` | Banner / reset paging |
| 401 `expired` | Refresh once, retry the request |
| 401 `session_revoked`, `refresh_reused`, `temp_password_expired`, other 401 | Sign out with a reason |
| 403 `password_change_required` | Go to Change password |
| 403 `forbidden` | Toast with the server message (they are written for users) |
| 404 | Not-found state in the page (also what scoped users see for out-of-scope FAs) |
| 409 | Code-specific UI: `version_mismatch`, `phone_taken`, `area_has_lead`, `allocation_exists`, `allocation_ended`, `in_use`, `issue_has_live_rule`, `rule_exists`, `draft_exists`, `not_draft`, `already_submitted`, `not_submitted`, `invalid_status`, `code_taken`, `email_taken`, `last_admin`, `lgd_code_taken`, `duplicate`; fallback "this changed since you opened it, reload" |
| 413 `payload_too_large` | "File too big" (2 MB JSON, 5 MB CSV import) |
| 429 `rate_limited` | Disable the action for `Retry-After` seconds |
| 503 `unavailable`, network errors | GETs retry with backoff (TanStack Query, max 3); mutations don't auto-retry |
| 500 `internal` | "Something went wrong" + `X-Request-ID` to quote to support |

Writes are not idempotent yet (no `Idempotency-Key`, backlog): disable submit buttons while a mutation is pending and
never auto-retry POSTs.

## Conventions

- Feature folders per nav area; route files thin. Query keys come from orval; invalidate by module after mutations.
- Tables: TanStack Table with server-side filtering only (no client sort across pages; the API sorts newest first).
- Dates: API is RFC 3339 UTC and `YYYY-MM-DD`; display in IST (`Asia/Kolkata`) with `date-fns` + `@date-fns/tz`
  (recommendation). Money: paise integers, format with `Intl.NumberFormat('en-IN', {style: 'currency', currency: 'INR'})`.
- Telugu fields sit next to English ones (`name` / `name_te`); render Telugu with `lang="te"` and Noto Sans Telugu.
- `@orbit/i18n`: a build script turns `i18n/en.json` and `i18n/te.json` into typed keys plus a tiny `t()`; farmer-web
  uses keys under `web.*` (Telugu default, English toggle). The portal's own UI copy stays in code (English).
- `@orbit/ui`: Style Dictionary turns `design/tokens/` into `tokens.css` (CSS variables, light + dark) and a
  Tailwind v4 `@theme` file the apps import (Tailwind v4 has no JS presets). shadcn components are copied into
  `packages/ui` and restyled with the tokens. Until `design/` exists, use shadcn defaults behind the same variable names.
- Runtime config: `config.json` (`apiBaseUrl`, feature flags) fetched before render, so one build runs in every
  environment (recommendation; matches "CI builds versioned artifacts, infra picks the version").
- Security headers via CloudFront response policy: CSP `default-src 'self'; connect-src 'self' <api origin> <s3 upload
  origin>; img-src 'self' data: blob: <s3 origin>; media-src 'self' blob: <s3 origin>; frame-ancestors 'none'`,
  HSTS, `Referrer-Policy: no-referrer` for farmer-web.

  lint, typecheck, unit tests, build both apps, Playwright with Postgres/Redis services and the Go API built from

## Deployment

- `pnpm build` produces `apps/ho-portal/dist` and `apps/farmer-web/dist`. CI uploads them as versioned artifacts
  (tags `ho-portal/vX.Y.Z`, `farmer-web/vX.Y.Z`); `infra/envs/<env>` pins which version CloudFront serves.
- ho-portal: the `ho-portal/` prefix of the env web bucket + its own CloudFront (e.g. `ho.<domain>`), SPA
  fallback to `/index.html`, long cache on hashed assets, no cache on `index.html` and `config.json`. Add its
  origin to the API's `CORS_ORIGINS`.
- farmer-web: own CloudFront distribution on the `FARMER_WEB_BASE_URL` host, `/web/*` from the `farmer-web/`
  prefix and `/v1/web/*` forwarded to the API (see above). Hashed assets cached long; voice prompts from
  `i18n/voice/te` served from CloudFront.
- Infra tasks for the infra plan: S3 CORS for presigned uploads from the portal origin, CloudFront path behaviours,
  security headers policy, WAF rate limits on `/v1/auth/*` (recommendation).
